# Файлы

Личное файловое хранилище: React, Node 24, SQLite и приватный S3. Общий пароль даёт владельцу загрузку, историю всех передач и удаление. Получатель получает случайную ссылку, при необходимости — отдельный пароль передачи. MCP не реализован; история API уже отсортирована по `created DESC`.

Основной экран: белый фон, «ЗАГРУЗИТЬ» размером 16 px по центру и шестерёнка справа сверху. Надписи «ЗАГРУЗИТЬ» и «СКАЧАТЬ» набраны локально поставляемым Manrope, без переноса и с размером 16 px. Срок, пароль скачивания и история находятся в шестерёнке. Вставка файлов из буфера также поддерживается. На странице получателя сведения скрыты в аккордеоне под иконкой; справа сверху — ссылка на загрузку. Production-домен: `files.example.com`.

## Запуск на server

Приложение развёрнуто отдельным Compose-проектом `holder` на https://files.example.com; сервисы example-app и example-app не изменяются. Используется существующий бакет `example-bucket`, исключительно префикс `holder/` (`S3_PREFIX=holder/`). Ключи объектов и multipart-запросы ограничены этим префиксом на уровне S3-адаптера. До запуска проверьте приватность, versioning/Object Lock и права на запись/удаление. Чужие префиксы не изменяются. У приложения должен быть ровно один процесс/контейнер: SQLite и сериализованная очередь рассчитаны на один экземпляр.

1. Скопируйте `.env.example` в `.env`, заполните параметры. `PUBLIC_URL` — точный origin HTTPS без пути; `ADMIN_PASSWORD` — случайный шестизначный цифровой пароль. `DOMAIN`, имя существующей внешней Docker-сети и resolver Traefik нужно согласовать с текущей конфигурацией сервера. `.env` не включён в git.
2. Настройте CORS по `deploy/cors.json`, заменив origin. Браузер должен видеть публичный S3 endpoint. Для multipart разрешены PUT и заголовки; ETag открыт. Сервер инициирует/завершает multipart, браузер получает только короткие разрешения конкретной части.
3. Добавьте правило из `deploy/lifecycle.json` к существующему lifecycle, не заменяя другие правила: `AbortIncompleteMultipartUpload` через 1 день. Это страховка от потерянных запросов/аварий; штатная уборка выполняется самим приложением.
4. Выдайте сервисному аккаунту только операции из `deploy/bucket-policy.json` для префикса `holder/` этого бакета. Замените placeholders и примените policy через аккаунт администратора; не выдавайте приложению управление IAM/бакетами или публичный доступ. Для Yandex минимальный набор S3-операций перечислен в шаблоне; проверьте policy в вашем облаке до запуска.
5. `docker compose config` → проверьте итог, затем `docker compose up -d --build`. Compose добавляет только сервис `flash`, отдельный volume и labels; Traefik и чужие сервисы не конфигурирует. Перед запуском проверьте, что router/service `flash` не заняты. Не запускайте команду в чужом compose-проекте.

HTTP→HTTPS redirect должен быть настроен на Traefik. Публичного порта backend в production Compose нет. `TRUST_PROXY_HOPS=1` подходит при одном Traefik между клиентом и приложением, без дополнительного CDN; иначе задайте корректное число. Логи Traefik тоже должны исключать URL передач, cookies и query подписанных S3-запросов. Само приложение не ведёт access log и не печатает секреты или сообщения SDK.

## Локально

`npm ci`, `npm run build`, загрузите переменные `.env` в окружение, затем `npm start`. Для разработки UI: `npm run dev`, backend на 3000; для полноценного same-origin режима используйте собранный UI на 3000. `.env` автоматически не читается, можно запускать `node --env-file=.env server/main.js`.

Тестовый S3: `docker compose -f compose.minio.yaml up --build`. MinIO console: localhost:9001, UI: localhost:3000. Учётные данные в этом файле **только тестовые**. Для браузера добавьте `127.0.0.1 host.docker.internal` в hosts, если это имя не разрешается вашей системой: endpoint должен совпадать для контейнера и браузера, иначе подпись недействительна. Альтернатива — запустить Node на хосте с S3_ENDPOINT=http://localhost:9000. MinIO volume содержит реальные тестовые файлы, в production этот stack не использовать. Образы MinIO в этом окружении не проверены: Docker отсутствует.

## Поведение и гарантии

- До 100 файлов и 2 000 000 000 байт исходников. Общая квота 20 000 000 000 байт. `BEGIN IMMEDIATE` резервирует исходники + будущий ZIP + запас ZIP-заголовков до создания multipart; готовые передачи не вытесняются. Разрешения частей живут 5 минут, размер каждой части подписан и затем сверяется по S3 ListParts, итоговый размер — по HEAD. Перезаписать завершённый объект этими разрешениями нельзя.
- Пауза/продолжение и три попытки на часть работают в открытой странице. Повторное продолжение перечитывает подтверждённые части на сервере. После закрытия страницы File-объекты теряются: незавершённую передачу можно удалить в истории или дождаться отмены через 24 часа. Возобновление после перезагрузки страницы не обещается.
- Несколько файлов — один ZIP без сжатия, поток S3→ZIP→S3. Части по 8 MiB, последовательно, с backpressure; полные файлы не пишутся на диск и не помещаются в память. Одновременно собирается один ZIP. Unicode, одинаковые имена и пустые файлы поддерживаются; пути нормализуются в безопасные уникальные имена. После HEAD-подтверждения ZIP исходники удаляются, состав остаётся в SQLite. До завершения этой очистки резерв не уменьшается.
- После аварии `archiving` повторяется с нуля, предыдущий ZIP/multipart удаляется; максимум три попытки, затем видимая ошибка. Для повторной передачи после исчерпания попыток удалите неудачную и загрузите заново. Multipart, потерянный между S3 create и записью SQLite, обнаруживается по префиксу при очистке или lifecycle. Восстановление требует сохранности SQLite volume.
- Ссылка появляется только в `ready`, TTL начинается в этот момент. Новые запросы, включая Range, блокируются сразу по `expires`; уже открытый S3 stream может закончиться после срока. Удаление сразу ставит `deleting`, не ждёт ZIP и не возвращает передачу в `ready`. Уборка запускается раз в минуту, освобождает квоту только после успешных S3 delete/abort. При отказе S3 резерв остаётся и история показывает ошибку.
- Постоянная ссылка скачивания проходит через Node/server, без локального файла. Есть HEAD, Content-Length, ETag, Last-Modified, одиночный Range, If-Range, If-Match, If-None-Match, даты условных запросов. Множественный Range возвращает 416. Защищённой передаче до пароля не раскрывается даже состав и срок; grant cookie живёт до 12 часов/срока и сбрасывается после рестарта. Общий пароль не подходит получателю.
- Пароли: scrypt со случайной солью; HttpOnly/SameSite=Strict/Secure cookies в HTTPS; обязательный точный Origin для изменений; login/unlock ограничены по IP. Сессии владельца в SQLite, 12 часов. Смена ADMIN_PASSWORD: перезапуск плюс удаление записей `sessions` для отзыва ранее выданных сессий.
- Контейнер: 1 CPU / 768 MiB, JS heap 384 MiB, журнал 3×5 MiB, read-only root и volume только для SQLite. SQLite/метаданные и Docker image занимают диск; **содержимое передаваемых файлов — нет**. Активные скачивания расходуют память на stream buffers и сеть; тяжёлые нагрузочные испытания ещё нужны.

Архивация работает отдельно от очереди upload API и очистки. Удаление прерывает текущий ZIP; резерв остаётся до прекращения записи и подтверждённой очистки. S3-запросы имеют connect/idle timeout и ограниченные повторы. Уборка раз в минуту предназначена для удаления в пределах 5 минут при исправном S3; фактический SLA на production и при полной квоте требует нагрузочного испытания.

## Проверки

`npm test` — backend HTTP/integration с in-memory S3 double: auth/privacy/Origin, strict expiry/delete, конкурентная квота, interruption/resume и потеря ответа complete, ZIP/Unicode/empty/duplicates, восстановление задачи, ограниченные retries и ошибки S3, HEAD/Range/If-Range/validators. `npm run build` — production UI. `npx playwright test` — Chrome, flow owner→upload→protected recipient→ZIP→delete и мобильная ширина. На Linux задайте `CHROME_PATH` или измените Playwright config на установленный браузер. UI fixture и фальшивый S3 находятся только в test и не входят в runtime.

См. `VALIDATION.md` для фактических результатов. Не проведены: реальный Yandex/MinIO, загрузка 2 ГБ, нагрузка/память на 768 MiB, длительные реальные browser pause/resume, Docker build/server. Перед production обязательно выполнить эти проверки с отдельным бакетом. Нет антивируса, превью содержимого, CDN, публичной регистрации, MCP или загрузок после закрытия вкладки.

Документация провайдеров: [Yandex multipart](https://yandex.cloud/en/docs/storage/concepts/multipart), [Yandex lifecycle](https://yandex.cloud/en/docs/storage/operations/buckets/lifecycles), [AWS multipart limits](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html).

Реальная S3-проверка: задайте `TEST_S3_ENDPOINT`, `TEST_S3_REGION`, `TEST_S3_BUCKET`, `TEST_S3_ACCESS_KEY`, `TEST_S3_SECRET_KEY` в окружении **отдельного тестового бакета**, затем `node --test test/real-s3.test.js`. Тест создаёт случайный префикс, загружает 9 MiB + пустой файл, пересоздаёт SQLite-соединение, собирает ZIP, проверяет байты, Range и удаление. Без endpoint он явно пропускается. Секреты не сохраняйте в командную историю или git.

## Автодеплой main

Приватный репозиторий: https://github.com/example-user/s3-flash-drive. Каждый push в main запускает backend-тесты, production-сборку и Chrome UI-тесты. Только после их успеха GitHub Actions собирает Docker image, передаёт его по SSH на server и обновляет исключительно Compose-проект holder через deploy/release.sh. Образ собирается на GitHub, не на занятом production-сервере. Релизы сериализованы, SHA фиксируется в .deployed-sha; при неуспешном healthcheck возвращается предыдущий образ/Compose.

Настройки Actions: vars.DEPLOY_TARGET, secrets.DEPLOY_SSH_KEY и secrets.DEPLOY_KNOWN_HOSTS. Ключ отдельный для этого проекта, host key закреплён. S3-ключи и пароль хранятся только в /root/apps/s3-flash-drive/.env на сервере и локальном .env, в GitHub и Docker image их нет. Шаблонный ADMIN_PASSWORD заменён случайным паролем в локальном .env. На server нужен Docker Compose с поддержкой --wait. Исходные файлы и образы релизов не смешиваются с example-app/example-app; чужие контейнеры/образы/тома не очищаются.

Для files.example.com access log Traefik отключён отдельными labels обоих routers, чтобы URL передач не попадали в общий журнал. Публичность бакета сохранена по явному решению владельца; пароль и срок строго проверяются при скачивании через домен, но прямой адрес S3 при его получении обходит эти проверки до физического удаления.

Интерфейс: Добавить + иконка копирования + QR без видимого URL; срок внизу справа. Настройки без видимых лэйблов, с доступными aria-label; генератор и копирование шестизначного пароля, иконки истории/выхода. Есть локальные иконки PNG/SVG, manifest и анимация с учётом prefers-reduced-motion. ADMIN_PASSWORD должен содержать ровно 6 цифр.
